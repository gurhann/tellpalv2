- (outcome) The room selected publication and revision modeling before choosing the STORY delivery format; user wants the outputs pressure-tested by multiple perspectives.
- (outcome) Publication model direction: one canonical content identity, one live pointer, and at most one active candidate per content + language + experience; candidate revisions should be immutable and edits create a replacement candidate with testing reset.
- (outcome) Revision operations should support reverting a promoted candidate to the previous live revision; rollback is scoped to content + language + experience, and active sessions remain pinned to their starting revision.
- (outcome) Revision/asset retention should be configurable by parameter rather than hard-coded; cleanup must respect live/rollback/session needs, with the concrete parameter and garbage-collection rules still open.
- (outcome) Revision retention is controlled only by backend/environment configuration; CMS does not set per-revision retention in the initial scope.
- (outcome) Sample story evidence: 24 numbered page JPG/MP3 pairs plus two Turkish cover JPGs; page images are 1712x2778 portrait, audio is mono MP3 192 kbps/48 kHz; folder is ~24 MB, pages+audio ~24.37 MB, total narration 8m44.6s. First 3 pages are ~3.38 MB and ~82.9s raw; a test ZIP was ~3.12 MB with deflate. This supports a small starter chunk but not a fixed final format.
- (outcome) Delivery decision: initial mobile release uses a revisioned manifest with separate per-page image/audio assets; ZIP is removed from the required first-release playback pipeline and may return later only if measurements or future offline/client needs justify it.
- (outcome) Manifest delivery direction: keep home/category/search responses small; fetch the full revisioned STORY manifest at detail or start, then schedule page assets from it.
- (outcome) Media access decision: Firebase Storage remains the media source; the backend checks entitlement/access before issuing short-lived URLs, and the mobile client downloads assets directly. No separate URL-generation charge is expected; material cost is driven by storage, download operations, and network egress. URL lifetime and optional backend caching remain implementation parameters.
