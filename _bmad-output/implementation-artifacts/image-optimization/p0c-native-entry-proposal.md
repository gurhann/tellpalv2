## 3. Runtime ephemeral provisioning, separately for each platform

The proposed mechanism is a host HTTPS broker plus a public-key pairing handshake tied to the trusted native test launcher. It is neither implemented nor empirically validated. The host driver owns its TLS private key and existing short-lived Firebase ID token in private host memory/files; the app obtains that token only at runtime. A TLS fingerprint/public key, scope, batch and nonce are public metadata, not bearer authorization. Their exposure cannot claim a session without proving possession of the paired app's fresh private key.

1. The host driver validates the private config, approved device alias and exact built app/test identities/signatures; creates a fresh broker session and challenge. It supplies only broker origin, public SPKI pin, scope/batch, public launch nonce and deadlines to the test launcher. Host/network diagnostics never dump the private config.
2. The experiment native bridge generates an ephemeral P-256 signing key in process memory for that launch. It verifies the broker's TLS identity using the supplied exact public pin, sends a public hello, and refuses redirects/alternate origins. Broker public hello/challenge responses contain no token. No private key is written to preferences, keychain, Android Keystore, files or test evidence.
3. The host driver binds the app's public key to this exact launcher/device session: Android instrumentation reports it through sanitized status from its target context; iOS UITest reads a temporary native accessibility element containing only this public key and reports it to the driver. The element is present only on the experiment bootstrap screen and is removed before journey timing. Host accepts no key taken solely from an unauthenticated network hello. An implementation must verify this public-key exchange on the chosen installed platform and retain the sanitized pairing receipt.
4. Broker issues a single-use challenge; bridge signs scope/batch/launch nonce/challenge. Host checks the paired key proof, expires/consumes the challenge, and delivers the runtime envelope over pinned TLS exactly once. Repeat, changed nonce/key, expired challenge/session, wrong app/batch/environment or excessive envelope fail closed. No secrets appear in `adb -e`, Xcode scheme/test-plan/xctestrun environments, Dart defines, packaged assets, native constants, UI/accessibility, logs or attachments.
5. Bridge hands the admitted bounded envelope to Dart through the experiment MethodChannel once, then drops native response buffers and bootstrap key references. Composition retains only the short-lived token needed by admitted HTTP requests. No refreshing Firebase session is installed on-device. Expiry/revocation ends admission and owner lifetimes; a new launch needs a new paired session. String copies/allocator behavior prevent claiming guaranteed byte zeroization; the promise is no deliberate persistence/export and bounded object lifetime, not forensic erasure.

Android: broker listens on host loopback; an authorized USB ADB reverse forwards a dedicated device-loopback port. Custom instrumentation uses `getTargetContext`, starts the experiment activity and reports the key from the native bridge; the existing `MainActivity` and Library harness are unused. Android documents target-context instrumentation and command-line `am instrument`; the proposed key/broker/bridge combination is our design and still needs validation. [Instrumentation API](https://developer.android.com/reference/android/app/Instrumentation), [command-line testing](https://developer.android.com/studio/test/command-line), [ADB transport](https://developer.android.com/tools/adb).

iOS/iPadOS: the paired UITest launches **ImageExperiment**, with public bootstrap metadata in `launchEnvironment`. The app reaches the private host's HTTPS broker on the explicitly allowed laboratory LAN; TLS pinning and app-key proof protect the runtime envelope. The host must restrict listener/network access, and local-network permission/ATS behavior needs physical validation before any token is sent. There is no assumed Apple USB port-forward feature in this design. Apple documents launch environment and P-256 signing; its APIs do not certify our pairing workflow. [XCUIApplication launchEnvironment](https://developer.apple.com/documentation/xcuiautomation/xcuiapplication/launchenvironment), [CryptoKit P-256](https://developer.apple.com/documentation/cryptokit/p256/signing/privatekey).

Neither platform path needs Flutter VM service configuration, LLDB, Java debugger or a credential form. Profile can expose profiling services; declare whether a tool attaches. Release AOT is proposed with no debugger attached, but instrumentation/UITest, the app bridge, laboratory signing, candidate server and driver lifecycle remain different from normal production launch. **Debugger-free does not mean production-identical lifecycle.** Verify actual attachment state; a `release` label or Xcode scheme setting alone is not evidence.

## 5. Concrete controlled candidate delivery and cache isolation

Propose a host-only HTTPS fixture service with `POST /experiment/v1/bootstrap/claim` and `GET /experiment/v1/batches/{batchId}/objects/{candidateId}`. These are new experiment-host routes, not existing backend APIs. `candidateId` is an opaque allowlisted entry ID; it is never a filesystem path or arbitrary remote URL. Each GET requires the runtime Firebase bearer token and current admitted batch/access session, verifies identity server-side and returns exact private frozen bytes with no redirect/raw-original fallback. Deny arbitrary path traversal, unknown entries, expired admission, changed revision and wrong UID. No upload, Firebase/GCS storage writes or public object access is introduced.

Host service reads only a private immutable manifest that binds corpus/reference/source/role/output hashes, MIME, bytes, dimensions, encoder/profile and the private exact file path. Before serving, independently reread/hash the actual files, then hold the admitted opened object or reverify the same identity on each read. Refuse a symlink/replacement/change and partial/oversized/corrupt body. A client adapter uses a manifest-backed object ID and verifies the delivered SHA/length/MIME/dimensions before admission to cache/decode. It must record actual decoded dimensions when available and preserve failure rather than replace the arm. Frozen per-input bounds remain explicit controls and require implementation tests; source-resolution offline success supplies none of these native checks.

Two separate cases are supported by the proposed adapter:

- **Current product role:** after the real backend has admitted exact catalog/detail metadata, map only an approved source asset/language/role/revision to its frozen control/candidate entry. Do not relabel a page illustration as a listing or hero asset. Existing screen framing, account/access/callback guards and accepted rendition/decode bounds remain unchanged. Record that candidate-byte network delivery is from the fixture host, while catalog metadata is from the local/test backend.
- **Isolated fixture role:** display the exact admitted raster in a separately identified slot through the new experiment route. This can measure that fixture's native decode/display/fixture-network behavior. It supplies no real reader turn, protected delivery, catalog eligibility, production CDN or end-user access result. The present offline page candidates do not automatically qualify for current listing/detail roles or reader geometry.

Control and candidate use the same host delivery/validation path in a selected comparison. Retain network payload bytes, actual request/retry/prefetch counts and cache outcomes; host serving cannot establish production Firebase/CDN wire cost. Keep storage across all variants separate from actual journey bytes.

Encoded namespace is a stable SHA-256 of `scope | batch | sessionGeneration | account/access alias | role | sourceRevision | profileRevision`; no runtime `hashCode` identity. Immutable object key also includes reference/source/output SHA, MIME/bytes/dimensions, arm and bounded decode geometry; attempt/provider keys retain current ownership suffixes. Namespace and all private resolved paths must be independently checked to stay under the experiment application's container. New session/account/access/revision creates a new namespace, never a cache alias.

Preserve current home/hero profile limits listed in section 1 with explicit profile arguments. The experiment binding sets the decoded control to 48 entries/32 MiB only in its isolated process. For disk-warm/decoded-cold, unmount and dispose target listeners/owners, await real pending transfer/decode settlement, verify absence of exact live/pending/provider keys, then retain only integrity-verified encoded files. For decoded-warm, retain the exact final resized provider key used by display. Evicting LRU counters alone does not establish cold ownership; Flutter exposes live/pending tracking separately. [ImageCache API](https://api.flutter.dev/flutter/painting/ImageCache-class.html).

## 6. Recorder, target-frame limitation and counters

Recorder records a bounded sanitized attempt ledger: monotonic clock domain/unit, scope/run/session generation, hashed source/reference/candidate/provider/decode identities, role/slot/DPR/fit/alignment, current-route visibility, request/response/retry IDs, bytes received, encoded verification, actual decoded dimensions, owner transitions and null/reason status for unavailable observations. Never record raw URLs, tokens, headers, exception strings/stacks, native device IDs, user IDs or bodies. Ring capacity, loss count, event caps and export deadlines must be frozen before Story 1.6.

Proposed immediate target probe receives the exact current decoded image/provider/attempt and wraps only the current onstage image render object. It can mark a UI paint-submission event when that image draws and reject placeholder/error/offstage, stale generation, departed route and wrong decode keys. It cannot call that event raster completion. `RenderObject.paint` describes submission into painting context; `addPostFrameCallback` follows the framework pipeline; `addTimingsCallback` reports batched frame timings. Those APIs by themselves do not associate a target render object's exact attempt with its completed engine raster frame. [RenderObject.paint](https://api.flutter.dev/flutter/rendering/RenderObject/paint.html), [post-frame callback](https://api.flutter.dev/flutter/scheduler/SchedulerBinding/addPostFrameCallback.html), [timing callback](https://api.flutter.dev/flutter/scheduler/SchedulerBinding/addTimingsCallback.html).

Therefore the default proposed record is `firstRasterizedTargetFrame: null`, reason `target_engine_frame_association_unverified`; physical presentation is separately null unless a verified tool observes it. Do not choose the first timing callback after decode as a substitute. A future association extension needs pinned Flutter engine/renderer/tool evidence that carries the same frame identifier from exact onstage target submission to completed raster work, plus stale/offstage/repaint/cache-layer and missing-frame tests. No such extension is currently implemented or proven by repository code. Android Window `FrameMetrics` is a window-level diagnostic, not an exact Flutter image-identity mapping. [FrameTiming](https://api.flutter.dev/flutter/dart-ui/FrameTiming-class.html), [Android FrameMetrics](https://developer.android.com/reference/android/view/FrameMetrics).

The concrete extension proposed in [protocol section 5](p0c-native-measurement-protocol.md#5-timing-and-actual-target-frame-association) replaces only the experiment rendering leaf with `NativeProbeImage` and an experiment `RenderImage` subclass using the same final bounded provider. It marks the actual admitted image draw with `PlatformDispatcher.instance.frameData.frameNumber`, then joins that marker to `FrameTiming.frameNumber` in the same engine/process run. A missing/default `-1` number, retained-layer ambiguity, offstage/occluded/stale image, lost timing or unverified clock mapping leaves the endpoint null. API availability and identity/clock behavior require exact compiled-engine and physical verification before this extension may supply a result; its detailed design does not change the default unavailable status.

Screenshot/`RenderRepaintBoundary.toImage` can support a separate quality/capture receipt, with timing and overhead disclosed. It cannot stand in for first physical presentation or first target raster completion. [Flutter capture API](https://api.flutter.dev/flutter/rendering/RenderRepaintBoundary/toImage.html).

Proposed counter adapters export observed decoded LRU/live/pending counts and per-attempt owner counts in-process. Profile DevTools Dart heap/external and raster counters, Android process PSS/RSS/native/graphics and Apple process footprint/allocation/graphics remain tool/device/permission-dependent. The [P0C protocol](p0c-native-measurement-protocol.md) and device matrix state actual availability; this proposal creates no numeric observation. Preserve separate overlapping counter families, sample gaps, attachment/observer overhead, absolute idle/peak/settled values and signed baseline deltas. The default proposed 1 Hz/30-second-settlement/five-observation settings require a later frozen batch; they are neither mobile budgets nor production reliability claims. [Flutter build modes](https://docs.flutter.dev/testing/build-modes).
