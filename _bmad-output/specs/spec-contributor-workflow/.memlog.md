topic: Contributor registry and content assignment workflow
updated: 2026-09-02T19:33
---

- (direction) CMS is a desktop-first editorial tool; contributor work is part of editing mobile-app content.
- (decision) Contributor assignments remain on the content detail screen and move directly after the selected-locale workspace because editors frequently alternate between descriptions, credits, and story pages.
- (capability) CAP-1 Contributor profiles carry one or more roles so editors can discover people by the work they can perform.
- (decision) A contributor profile must always have at least one role and may have multiple roles.
- (constraint) Initial role catalog is fixed to AUTHOR, ILLUSTRATOR, NARRATOR, and MUSICIAN; translator and editor roles are deferred.
- (capability) CAP-2 Content assignments select exactly one role from the contributor profile while preserving optional language scope and credit-name override.
- (capability) CAP-3 Editors can search contributors by display name and role through database-backed paginated results rather than a recent in-memory subset.
- (capability) CAP-4 Editors can create a missing contributor inline from the role-scoped assignment flow and have the new record assigned immediately.
- (decision) Inline creation asks only for display name and roles; the initiating role is preselected.
- (decision) AUTHOR, ILLUSTRATOR, and MUSICIAN assignments default to all languages; NARRATOR defaults to the currently selected content language; advanced settings may change scope.
- (capability) CAP-5 Existing content contributors are grouped by role and language scope with direct add, edit, remove, and reorder actions.
- (decision) New assignments receive the next order automatically; editors reorder only within the same role and language group using direct manipulation, never a numeric sortOrder field.
- (capability) CAP-6 The system prevents duplicate contributor identities using a normalized display-name uniqueness rule and redirects editors to the existing result.
- (decision) Display-name duplicate comparison ignores case and leading/trailing whitespace.
- (capability) CAP-7 Editors can add and remove profile roles while the system blocks removing a role still used by content assignments and exposes usage count plus affected-content links.
- (capability) CAP-8 Existing contributor roles are backfilled from distinct historical content assignments during migration without losing credits.
- (capability) CAP-9 The contributor registry shows role chips, supports name and role filters, uses database-backed pagination, and offers create/edit/delete management.
- (constraint) Contributor and assignment data remain owned by the existing content module and preserve Spring Modulith boundaries.
- (constraint) Registry filtering, ordering, and paging must follow ADR-0009 and must not load all contributors for client-side filtering.
- (constraint) Contributor UI copy must support Turkish and English through the CMS i18n layer.
- (non-goal) This delivery does not add contributor biography, portrait, social links, public profile pages, new role types, or mobile/public contributor APIs.
- (assumption) Profile roles are eligibility metadata; an assignment role must exist on the contributor profile.
- (assumption) A dedicated contributor detail route is unnecessary in the first delivery; registry dialogs and content-detail controls cover the agreed workflow.
- (question) How should migration assign a mandatory role to existing contributors that have no historical content assignments?
- (question) If existing contributor names collide after trim and case normalization, should migration merge them or stop with a remediation report?

- (decision) Existing contributors with no historical content assignments receive AUTHOR during role backfill.
- (decision) If existing contributor display names collide after trim and case normalization, migration must report the collisions and stop; it must not merge identities automatically.
