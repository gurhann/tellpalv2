This is local resolution evidence, not an independently rerun SDK/version command or platform build.
- Library and recommendation previews share `PreviewCard`. Device selection uses logical `shortestSide >= 600`; tablets choose tablet cover or fall back to phone, phones choose phone: `app/mobile/lib/core/preview/presentation/widgets/preview_card.dart:41-44`. It uses CachedNetworkImage with memCacheWidth 360/600 and BoxFit.cover, then renders an Image under the same ResizeImage sizing: `:198-240`. No devicePixelRatio or actual slot dimension enters this decoder target. No maxWidthDiskCache/maxHeightDiskCache is set there: decoding does not shrink the HTTP payload.
- StoryDetail Hero decoder targets preserve descriptor aspect ratio with `s = min(1, capW/sourceW, 2048/sourceH, sqrt(4194304/(sourceW*sourceH)))`, where capW is 1080 phone/1600 tablet; each output edge is floored and at least 1: `app/mobile/lib/features/story_detail/presentation/widgets/story_detail_hero.dart:16-28`. Source dimensions are therefore not upscaled by this target calculation. Both memCacheWidth and memCacheHeight are passed; rendering reuses the bounded ResizeImage provider: `:144-172,199-203`. The limits do not use actual slot size or DPR. The 4,194,304 pixel/16 MiB decoded-pixel ceiling is a policy ceiling, not measured process memory; the combined width/height caps already imply tighter maxima of 2,211,840 pixels phone and 3,276,800 tablet.
- Hero metadata admission accepts JPEG/PNG, encoded bytes <=20 MiB and positive dimensions totaling <=40,000,000 source pixels: `app/mobile/lib/features/story_detail/data/repository_impl/story_detail_repository_impl.dart:58-69`. StoryDetailImageCache checks actual cached-file size <=20 MiB and SHA-256 against the admitted source identity before delivering: `app/mobile/lib/core/network/story_detail_image_cache.dart:38-46`. This does not avoid downloading source bytes or establish peak decoder/native/GPU memory.

## Actual slot geometry and physical sizing

Let viewport logical size be W×H and DPR be d. Values below are geometry calculated from code, not measured devices.

| Slot | Logical dimensions | Physical display box |
| --- | --- | --- |
| Library card | height = .230H + 16; width = .75 × height | d×width by d×height |
| Detail recommendation card | same as Library | same |
| Detail Hero phone | full available body width W, height = W/.9 | dW by dW/.9 |
| Detail Hero tablet | full available body width W, height = W/1.1 | dW by dW/1.1 |

References: `app/mobile/lib/features/library/presentation/view/library_view.dart:205-207,241-251`; `app/mobile/lib/features/story_detail/presentation/view/story_detail_view.dart:112-123,163-177,482,494-504`. The Hero lives in a full-width vertical ListView with no horizontal padding; cards have 16 dp horizontal list padding/gap, not an additional inset inside each slot. Selection at shortestSide >=600 is independent of orientation and window width.

For existing logical test sizes (411×914 and 800×1280), card slots are respectively 169.665×226.22 and 232.8×310.4 dp; Hero slots are 411×456.667 and 800×727.273 dp. These widget matrices explicitly use DPR 1: `app/mobile/test/story_detail/story_detail_view_test.dart:83-93`; `app/mobile/test/library/library_view_test.dart:81-88`. They do not by themselves qualify high-DPR sharpness.

For aspect-preserving BoxFit.cover, a source Ws×Hs must provide `k = max(d*slotW/Ws, d*slotH/Hs)` and a matching decoded size approximately `k*Ws × k*Hs`, capped at available source pixels; a width-only physical target is insufficient when height determines cover scaling. This describes required resolution, not a new adopted profile.

Illustrative high-resolution wide source 8000×5000: current Hero targets are 1080×675 phone and 1600×1000 tablet **before** BoxFit.cover. At phone 411 dp/DPR3 the cover fit needs about 2192×1370 source-proportional decoded pixels; at tablet 800 dp/DPR2 it needs about 2327×1455. Current decoded outputs would be enlarged by approximately 2.03× and 1.45× respectively. These are hypothetical quality risks from geometry, not observed blur or approved reasons to increase the budgets. Tablet landscape (1280 dp width) further increases requirements even though the same 1600-width cap is selected.

All preview and Hero images use cover cropping. For a 512×909 tall source, the fraction of source height visible is (512/909)/slotAspect: about 75.10% in a 3:4 card, 62.59% in phone Hero (.9), and 51.21% in tablet Hero (1.1). Remaining source height lies outside the box. This may be inherited intended presentation rather than a bug; source-preserving server conversion cannot guarantee that baked title/text remains visible. Explicit framing/title inspection is required before choosing renditions. Architecture leaves image crop policy/device media budgets to measurement: architecture spine `:165`.

## Cache, ownership, refresh and prefetch

- Preview immutable disk identity is account/access + UI context language + contentId + assetId; transfer identity appends catalogAttempt, widget owner, artwork attempt: `app/mobile/lib/core/preview/presentation/widgets/preview_card.dart:117-122`. Hero immutable identity is account/access + contentLanguage + assetId + checksum; transfer appends detail attempt and heroAttempt: `app/mobile/lib/features/story_detail/presentation/widgets/story_detail_hero.dart:135-142`. Signed URL is not the persistent disk identity. New rendition adoption must preserve immutable output identity/checksum semantics; do not key only by an expiring URL.
- Shared Library cache profile is account/access scoped, stale period 10 minutes, 80 objects, with 90 owned attempts by default: `app/mobile/lib/core/network/library_image_cache.dart:18-27,70-75`. Its generic profile defaults used by Hero are 4 owned attempts, 20 files, 100 MiB disk, 20 MiB per transfer: `:45-66`; separate Hero namespace/object config is `app/mobile/lib/core/network/story_detail_image_cache.dart:8-19`. Encoded disk/transfer and decoded ImageCache limits are distinct layers.
- Stable disk warm hits are validated before return (`app/mobile/lib/core/network/library_image_cache.dart:371-383`); exact unfinished cold source sharing includes immutable key, URL, sorted headers and progress mode (`:234-246`). Changed URL/namespace cannot join that cold flight. Transfer bytes are promoted only after successful image decode and current owner checks (`app/mobile/lib/core/preview/presentation/widgets/preview_card.dart:212-227`; Hero `:169-197`; cache `:693-710`). Promotion reads full encoded bytes, and may read prior encoded bytes too (`library_image_cache.dart:750-769`); account for those buffers in real memory measurement.
- Hero disposal evicts its exact bounded provider and releases its transfer (`story_detail_hero.dart:73-79`); recovery prevents retained-URL retries until fresh metadata (`:130-134`). Cache release cancels and waits for the old writer before cleanup (`library_image_cache.dart:714-729`). Native transfer has response-header/body-idle/total bounds and enforces bytes while streaming (`library_transfer_file_service.dart:13-15,62-95,171-180`). These are cancellation/renewal semantics; no HTTP byte-range resume is implemented in inspected image transport.
- Library/detail use lazy ListView builders/separated lists (`library_view.dart:243-251`; detail view `:113-151,496-519`). No explicit precacheImage/prefetch exists in those features. Normal scroll viewport/cacheExtent behavior can still construct nearby artwork; that is distinct from an application prefetch policy.
- Older reader PoC explicitly precaches current full NetworkImage, then the next image after media readiness (`app/mobile/lib/story_player_page.dart:119-142,216-227`). Actual reader uses Image.network without cacheWidth/cacheHeight and BoxFit.contain in an Expanded safe-area region (`:325-357`). It is URL-keyed (`:340-343`), refreshes the pinned revision (`:154-169,199-213`), and its page dimensions are parsed but not used for decoder sizing (`app/mobile/lib/story_manifest.dart:51-70`). This path needs separate future reader design/qualification; it is not evidence that Story1.2 Hero currently decodes unbounded.

No measured OOM, device memory leak, jank, actual blur, new network-saving percentage or production performance improvement is established by this inspection. The actionable research gaps are representative high-resolution/page inputs, actual DPR/slot fit, framing and baked-text legibility, cold/disk-warm/memory-warm transferred bytes, first onstage paint, and native/process peak/settled memory under bounded ownership.
