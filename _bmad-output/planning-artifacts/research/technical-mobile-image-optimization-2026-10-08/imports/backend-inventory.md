## 2. Detail and ordinary page delivery

- Controlled Story 1.2 detail verifies an `ORIGINAL_IMAGE` JPEG/PNG, actual source metadata, complete byte count and SHA (`be/src/main/java/com/tellpal/v2/asset/application/StoryDetailHeroQueryService.java:48–64`). Its verifier subsamples decode to roughly 1600×2048 rather than decoding the full 40-million-pixel source (`:75–82`), but signs the original object path and returns the original asset ID/byte size (`:85–87`). This reduces verification allocation; it does not reduce the client's payload.
- Hero verification owns four semaphore slots with virtual-thread workers and an at-most-8-second wait (`:27–46`). Cancellation requests interruption; the slot is released in the actual worker's `finally` (`:41–42`). No worker/client memory or cancellation latency was measured here.
- Legacy public story pages still load each localized `illustrationMediaId`, and map that record directly (`be/src/main/java/com/tellpal/v2/content/application/query/PublicContentQueryService.java:123–142`; `PublicContentQueryMapper.java:61–74`). They do not consume the experiment manifest.
- Legacy asset bundles gate on completed processing and look up generated paths (`be/src/main/java/com/tellpal/v2/asset/application/ContentAssetBundleService.java:50–80`). This is a separate contract from the verified listing store.

## 3. Revision, publication and reuse

- Listing revision hash includes content, language, source asset ID, observed source SHA and profile (`ListingCoverProcessingExecutor.java:42`). Preparation reuses an existing ready row by content/language/source ID/profile before scheduling (`be/src/main/java/com/tellpal/v2/asset/application/LibraryCoverPreparationService.java:24–31`). It does not re-encode on every GET or every preparation request.
- Listing publication pessimistically locks the job, fences processing ID/attempt/lease/source/profile, checks captured manifest identity, saves the revision and completes within one transaction (`LibraryCoverPreparationService.java:33–41`; `be/src/main/java/com/tellpal/v2/asset/domain/AssetProcessing.java:65–77`). Both successful and failed callbacks require ownership (`AssetProcessingService.java:153–170`); stale executor failures are ignored (`ListingCoverProcessingExecutor.java:50–55`).
- Listing store lookup/uniqueness is source asset ID + profile, while the stored revision includes source SHA (`be/src/main/java/com/tellpal/v2/asset/infrastructure/persistence/JdbcListingCoverRevisionStore.java:12–25`). Reuse freshness therefore depends on the source-identity/immutability contract. This is not evidence of mutated originals or an observed defect.
- Page jobs are scheduled from ordered localized page/source/audio identities after edits (`be/src/main/java/com/tellpal/v2/content/application/StoryPageManagementService.java:114–158`). Revision hash additionally incorporates actual image SHA and profile (`RegisteringAssetProcessingJobExecutor.java:136–147`). Sources are read once for fingerprints and again before transformation; changed SHA/ID is rejected (`:184–196`). Audio remains the existing asset ID.
- Page outputs are real uploaded/reread bytes with MIME/size/hash/decodability checks (`RegisteringAssetProcessingJobExecutor.java:155–170`, `:233–247`). The path includes `revisions/{hash}/pages/{pageId}.jpg` (`:253–255`). Existing manifest rows are retained/reused by revision (`be/src/main/java/com/tellpal/v2/asset/infrastructure/persistence/JdbcStoryPageMediaManifestStore.java:31–55`). The executor still transforms and uploads before registry reuse; this is not an encode-skip cache.
- Page manifest save is transactional, but executor manifest publication and job completion are separate calls (`RegisteringAssetProcessingJobExecutor.java:172–180`). Captured-attempt checks and pessimistic completion/failure load currently apply specifically to `LISTING_COVER` (`be/src/main/java/com/tellpal/v2/asset/application/AssetProcessingService.java:153–170`, `:315–320`). This establishes a source-level hardening requirement before production admission, not a reproduced race.
- The experiment endpoint verifies Firebase identity and allowlist, then requires current ordered snapshot matching for the latest revision; explicit retained revisions remain available (`be/src/main/java/com/tellpal/v2/user/web/mobile/TestStoryPageMediaController.java:73–108`). This does not establish production entitlement or a production ready/live contract.
- Publication itself only invokes editorial policy and saves (`be/src/main/java/com/tellpal/v2/content/application/ContentPublicationService.java:42–47`). Story policy checks active content, description, cover and localized page text/audio/illustration references (`be/src/main/java/com/tellpal/v2/content/domain/StoryPublicationReadinessPolicy.java:14–56`). It does not require verified renditions.
- Listing preparation is a separate explicit admin use case (`ContentManagementService.java:73–80`). Create/update accept status/processing state (`:135–179`); manual processing mutation and `markAsReady` remain (`:190–210`). Legacy visibility is `PUBLISHED && COMPLETED` plus required body (`be/src/main/java/com/tellpal/v2/content/domain/ContentLocalization.java:140–153`); only `DELIVERY` status events update localization state (`AssetProcessingStatusListener.java:19–30`). A new gate must account for all these paths.

## 4. Resource, color, alpha and orientation facts

- Both transformation processors call `reader.read(0)` after inspecting the 40-million-pixel cap; they do not configure source subsampling. They retain full source bytes, decoded source and RGB output during processing (`ListingCoverRenditionProcessor.java:49–70`; `PageImageRenditionProcessor.java:51–72`). A 40-million-pixel 4-byte raster alone would be about 160 MB decimal; this is a rough allocation model, not measured peak heap/RSS. Decoders, compressed buffers, temporary ImageIO cache and verification allocations require measurement.
- Listing invokes the complete conversion twice sequentially for phone then tablet (`ListingCoverProcessingExecutor.java:43–44`). Page processing works one source at a time after a fingerprint pass (`RegisteringAssetProcessingJobExecutor.java:136–160`), avoiding retention of the full story's decoded images.
- Current poller batch size defaults to 10, capped at 100, but its `for` loop invokes processing synchronously (`be/src/main/java/com/tellpal/v2/asset/infrastructure/processing/AssetProcessingPoller.java:33`, `:64–79`). Do not infer 10-way decoding from batch size. Multiple instances, future worker pools and overlapping lease recovery are separate scaling concerns; no current replica topology or concurrent memory measurement was obtained.
- White matte and RGB/JPEG output explicitly discard alpha semantics. No explicit EXIF transpose, animation iteration/timing/disposal or general ICC normalization policy appears in these converters. They read image zero and write `IIOImage(output, null, null)` (`ListingCoverRenditionProcessor.java:54–81`; `PageImageRenditionProcessor.java:56–83`). This proves no animation-preserving path.
- Existing measured local evidence must qualify any stronger color statement. `_bmad-output/specs/spec-publish-time-image-optimization/p0-small-jpeg-findings.md:39–43` reports seven samples decoded to sRGB under the exact Java reader sequence; same-size RGB drawing retained decoded pixels. One P3 sample closely matched explicit Pillow/LittleCMS P3→sRGB before resizing/lossy encoding. ICC removal alone is not proof of unmanaged colors. This sample does not prove gamut preservation or general ICC handling. All selected samples lacked EXIF orientation (`experiments/color-diagnostic/README.md:23`). These are existing measurements, not this inventory's rerun.
- ADR-0010 preserves separate STORY source, localized reading and shared listening artwork; LULLABY static listing artwork is separate from potentially animated listening/detail GIF (`be/docs/adr/ADR-0010-content-cover-ownership.md:17–26`). A generic JPEG job cannot certify all those roles.

## 5. Existing experiment evidence and draft consistency

The existing bounded experiment, not rerun here, contains six matched small legacy cover controls plus one separate P3 diagnostic, 63 candidate files, no reader pages and no source larger than 909-pixel longest edge (`p0-small-jpeg-findings.md:7–13`). Six control originals total 269,651 bytes; source-resolution q85 totals 383,718 bytes (+42.30%, 6/6 larger). Listing phone q85 totals 207,255 bytes (−23.14%, 2/6 larger); tablet q85 totals 371,916 bytes (+37.92%, 5/6 larger) (`:17–35`). These are frozen offline corpus alternatives, not journey downloads, storage totals or production-distribution measurements. Worker peak memory, native device quality and production profile approval remain unestablished (`:41–45`, `:53`).

No substantive contradiction was found in the current draft's central inventory or rollout decision. `brownfield.md:9–18` correctly distinguishes verified listing/page conversion, original detail delivery and legacy plan-only work; its full-decode risk and color qualification (`:53`) are appropriate. Three precision additions are useful:

1. Do not imply the page verification is as strong as listing verification: page processor checks allowed declared MIME but does not explicitly compare decoder format to MIME; page stored verification checks decodability but does not compare decoded output dimensions to recorded dimensions (`PageImageRenditionProcessor.java:41–56`; `RegisteringAssetProcessingJobExecutor.java:233–247`). The listing path explicitly checks both. These are inspection findings, not exploited or reproduced failures.
2. Distinguish reuse mechanisms: listing preparation can skip work for an existing ready source/profile; page processing repeats transformation/upload before registry/manifest reuse. Neither current converter implements a general small-source pass-through policy. OQ-3 remains open, as the draft says.
3. Record the synchronous poller and Hero verifier's existing subsampling when discussing concurrency/memory. The draft's statement that source conversion fully decodes is correct; it should not be generalized to Hero's query verifier or mistaken for evidence of a 10-converter pool.

The draft's planned requirement to verify observed MIME/dimensions/hash and fence all production publication jobs is therefore prospective. It should not be represented as already implemented across every image path.
